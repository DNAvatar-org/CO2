Analyse de Performance - Algorithmes de Calcul Radiatif

Vue d'ensemble

Le système de simulation radiatif utilise deux algorithmes principaux en cascade :

  1. Algorithme de convergence (dichotomie) : trouve la température de surface T₀ qui équilibre le flux radiatif
  2. Algorithme de transfert radiatif : calcule le flux réémis à chaque couche atmosphérique avec tropopause

1. Algorithme de Convergence (Dichotomie)

Localisation

  • Fichier : API_BILAN/radiative/calculations.js
  • Fonction : simulateRadiativeTransfer()
  • Moteur principal (convergence cycle eau + dichotomie) : computeRadiativeTransfer() dans API_BILAN/convergence/calculations_flux.js (vue Scientifique et visu)

Description

Méthode de dichotomie (bisection) pour trouver T₀ telle que :

flux_total(T₀) = flux_solaire_absorbé(T₀)

Complexité temporelle

O(log₂(1/ε)) × O(transfert_radiatif)

Où :

  • ε = tolérance = 0.1 W/m²
  • O(transfert_radiatif) = complexité du calcul de flux (voir section 2)

En pratique :

  • Intervalle initial : ±50K autour de T₀_initial
  • max_iterations = 20 (limite fixe)
  • Complexité réelle : O(1) car limité à 20 itérations maximum

Nombre d'itérations

  • Minimum : ~5-7 itérations (convergence rapide)
  • Maximum : 20 itérations (limite fixe)
  • Moyenne : ~10-12 itérations

Coût par itération

Chaque itération appelle calculateFluxForT0() (dans API_BILAN/radiative/calculations.js) qui effectue le calcul complet du transfert radiatif (voir section 2).

2. Algorithme de Transfert Radiatif (Flux Réémis)

Localisation

  • Fichier : API_BILAN/radiative/calculations.js
  • Fonction : calculateFluxForT0()
  • Boucle principale : double boucle (troposphère puis stratosphère) sur z_range × lambda_range

Description

Calcule le flux radiatif montant à travers toutes les couches atmosphériques pour chaque longueur d'onde.

Structure de la boucle

// Parcourir chaque couche d'altitude
for (let i = 0; i < z_range.length; i++) {
    const z = z_range[i];
    const T = temperature(z, CO2_fraction, T0_test); // ⚠️ Recalcule z_trop à chaque appel !
    const n_CO2 = airNumberDensity(z, CO2_fraction, T0_test) * CO2_fraction;

    for (let j = 0; j < lambda_range.length; j++) {
        const lambda = lambda_range[j];
        // Calculs : absorption, émission, flux sortant
    }
}

✅ Optimisation implémentée : Tropopause

Observation :

  • Avant tropopause : T(z) = T₀ + Γ × z (gradient linéaire) - calculs complets nécessaires
  • Après tropopause : T(z) = T_trop (constante) - calculs simplifiables

Problème :

  • La tropopause dépend de T₀ : z_trop = f(T₀) (8-17 km selon T₀)
  • T₀ change à chaque itération de dichotomie
  • Donc z_trop change aussi !

✅ Optimisations implémentées :

  1. ✅ Calculer z_trop et T_trop une seule fois au début de calculateFluxForT0()
  2. ✅ Séparer la boucle en deux parties : i < i_trop et i >= i_trop
  3. ✅ Après tropopause : T est constante, mais n_CO2 et n_H2O varient encore (densité ↓ avec z)
  4. ✅ Précalculer les fonctions de Planck pour T_trop (une fois par λ, pas par z)
  5. ✅ Précalculer les sections efficaces CO₂ et H₂O (une fois par λ, pas par couche)

Paramètres de grille (valeurs par défaut)

Paramètre Valeur Description
z_max 120,000 m Altitude maximale
delta_z 50 m Pas d'altitude
lambda_min 0.1 × 10⁻⁶ m Longueur d'onde minimale
lambda_max 100 × 10⁻⁶ m Longueur d'onde maximale
delta_lambda 0.1 × 10⁻⁶ m Pas de longueur d'onde

Nombre de points

Couches d'altitude (z_range) :

n_z = z_max / delta_z = 120,000 / 50 = 2,400 couches

Longueurs d'onde (lambda_range) :

n_λ = (lambda_max - lambda_min) / delta_lambda
   = (100e-6 - 0.1e-6) / 0.1e-6
   = 99.9e-6 / 0.1e-6
   = 999,000 longueurs d'onde

Total de points (x × y) :

N_total = n_z × n_λ = 2,400 × 999,000 ≈ 2.4 × 10⁹ points

Complexité temporelle

O(n_z × n_λ) = O(2,400 × 999,000) ≈ O(2.4 × 10⁹)

Opérations par point :

Avant tropopause (z < z_trop, ~8-17 km) :

  • Calcul de température : T(z) = T₀ + Γ × z → O(1)
  • Calcul de densité CO₂/H₂O : O(1)
  • Calcul de section efficace : O(1)
  • Calcul d'absorption : O(1)
  • Calcul d'émission (Planck) : B_λ(T(z)) → O(1) (T varie)
  • Calcul de flux sortant : O(1)
  • Total : ~7-8 opérations par point

Après tropopause (z ≥ z_trop, ~17-120 km) :

  • Calcul de température : T(z) = T_trop (constante) → O(1) mais redondant ⚠️
  • Calcul de densité CO₂/H₂O : O(1) (varie avec z, densité ↓ exponentielle)
  • Calcul de section efficace : O(1)
  • Calcul d'absorption : O(1)
  • Calcul d'émission (Planck) : B_λ(T_trop) → O(1) mais pourrait être précalculé ⚠️
  • Calcul de flux sortant : O(1)
  • Total : ~7-8 opérations par point (mais optimisable)

✅ Optimisations implémentées :

  • ✅ Précalculer B_λ(T_trop) pour toutes les λ une fois → économie de ~n_λ × n_z_above opérations
  • ✅ Éviter le recalcul de z_trop dans temperature() → économie de ~n_z appels
  • ✅ Précalculer les sections efficaces CO₂ et H₂O → économie de ~2 × n_z × n_λ appels
  • Gain estimé : ~15-25% de réduction du temps de calcul

Opérations totales par itération :

N_ops = 2.4 × 10⁹ × 7 ≈ 1.68 × 10¹⁰ opérations

Complexité spatiale (mémoire)

Tableaux 2D :

  • upward_flux[n_z][n_λ] : 2.4 × 10⁹ valeurs
  • optical_thickness[n_z][n_λ] : 2.4 × 10⁹ valeurs
  • emitted_flux[n_z][n_λ] : 2.4 × 10⁹ valeurs
  • absorbed_flux[n_z][n_λ] : 2.4 × 10⁹ valeurs

Total : ~4 × 2.4 × 10⁹ × 8 bytes ≈ 77 GB (théorique)

En pratique, JavaScript optimise et les tableaux sont alloués dynamiquement.

3. Complexité Globale

Complexité totale

O(iterations_dichotomie × n_z × n_λ)

Avec :

  • iterations_dichotomie ≈ 10-12 (moyenne)
  • n_z = 2,400
  • n_λ = 999,000

Complexité pratique :

O(12 × 2,400 × 999,000) ≈ O(2.88 × 10¹⁰)

Temps d'exécution estimé

Hypothèses :

  • CPU moderne : ~3 GHz = 3 × 10⁹ opérations/seconde
  • Efficacité JavaScript : ~30% (interprétation, GC, etc.)
  • Performance réelle : ~10⁹ opérations/seconde

Temps par calcul complet :

T = (2.88 × 10¹⁰) / (10⁹) ≈ 28.8 secondes

En pratique : 20-40 secondes selon le matériel et les optimisations du navigateur.

4. Impact sur le FPS

Calculs par frame

Si le calcul est exécuté de manière synchrone :

  • FPS : 0 (blocage total pendant le calcul)
  • Expérience utilisateur : gel complet de l'interface

Optimisations actuelles

  1. Callback / récepteur : l’API émet compute:progress et cycleCalcul ; affichage progressif (organigramme, convergence) pendant le calcul
  2. Grille spectrale : grille λ adaptative (zones CO₂/CH₄/H₂O densifiées) et lambda_weights ; option homogène disponible
  3. Tropopause : calcul unique z_trop / T_trop, boucles troposphère / stratosphère séparées, précalcul Planck et sections efficaces (voir section 2)

Stratégies d'optimisation possibles

A. Réduction de la grille

  • delta_z : 50m → 100m → n_z : 2,400 → 1,200 (×2 plus rapide)
  • delta_lambda : 0.1μm → 0.2μm → n_λ : 999,000 → 499,500 (×2 plus rapide)
  • Gain total : ×4 plus rapide

B. Calcul adaptatif

  • Calculer uniquement les longueurs d'onde importantes (bande CO₂ ~15μm)
  • Ignorer les longueurs d'onde où l'absorption est négligeable

C. Parallélisation (Workers)

  • Web Workers pour calculer plusieurs bandes spectrales en parallèle (tranches λ)
  • SIMD (si disponible) pour les calculs vectoriels

D. Cache et précalcul

  • Mettre en cache les sections efficaces (dépendent uniquement de λ)
  • Précalculer les profils de température pour T₀ courantes

E. Optimisation tropopause ⭐ IMPLÉMENTÉ

  • ✅ Calculer z_trop et T_trop une seule fois au début de calculateFluxForT0()
  • ✅ Séparer la boucle : for (i < i_trop) et for (i >= i_trop)
  • ✅ Précalculer B_λ(T_trop) pour toutes les λ (une fois, pas par couche)
  • ✅ Précalculer sections efficaces CO₂ et H₂O (une fois, pas par couche)
  • Gain estimé : ~15-25% de réduction du temps de calcul
  • Complexité : O(1) pour trouver i_trop, puis deux boucles séparées

5. Workers (API_BILAN/workers/)

Fichiers présents

  • API_BILAN/workers/spectral_slice_worker.js : worker qui calcule une tranche spectrale (sous-ensemble de λ). Reçoit lambda_range, layers (z, T, n_CO2, n_H2O, n_CH4, etc.), sections efficaces précalculées, earth_flux ; retourne total_flux_slice et upward_flux pour cette tranche. Constantes (Planck, c, k_B) passées dans le message (depuis window.CONST côté main). Permet en principe de paralléliser par bandes de longueur d’onde (plusieurs workers, chacun une tranche λ).
  • API_BILAN/workers/compute_worker.js : stub (envoie ready, sur run répond stub – compute not yet in worker). Prévu pour déporter à terme computeRadiativeTransfer() / cycles de convergence dans un worker, afin de garder le thread principal pour la GUI/DOM.

État actuel

Le calcul radiatif complet (dichotomie + calculateFluxForT0()) s’exécute aujourd’hui sur le thread principal. Les workers sont en place pour une évolution future :

  • spectral_slice_worker : logique de tranche prête ; reste à brancher depuis API_BILAN/radiative/calculations.js (découper lambda_range en N tranches, lancer N workers, agrégation des résultats).
  • compute_worker : migration de la boucle de convergence (cycle eau + dichotomie) à faire ; objectif = ne plus bloquer le main thread pendant les 20–40 s de calcul.

6. Recommandations

Pour maintenir un FPS acceptable (>30 FPS)

  1. Calcul asynchrone obligatoire : ne jamais bloquer le thread principal
  2. Précision adaptative :
    • Pendant le calcul : delta_z = 100m, delta_lambda = 0.2μm
    • Après convergence : delta_z = 50m, delta_lambda = 0.1μm
  3. Limite de temps par frame : max 16ms (60 FPS) ou 33ms (30 FPS)
  4. Indicateur de progression : barre de progression pour l'utilisateur

Métriques de performance

  • Temps de convergence : < 5 secondes (objectif)
  • FPS minimum : > 30 FPS pendant le calcul
  • Mémoire : < 500 MB (objectif)
